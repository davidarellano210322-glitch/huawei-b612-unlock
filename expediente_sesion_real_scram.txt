POR QUÉ HACÍA FALTA ESTA RONDA
---------------------------------------------------------------------
El 108006 del router real es el MISMO para "contraseña incorrecta" y
para "prueba SCRAM mal calculada": con 108006 NO se puede saber si el
cliente calcula bien el proof. Además, el login fallido también rota el
token (authentication_login.lua), así que el flujo completo nunca se
había visto con un login EXITOSO. Si el cliente tuviera un bug, el
primer intento con la contraseña del sticker fallaría de forma
ambigua (y los intentos de login son limitados: 108007 con waittime).

QUÉ SE HIZO
---------------------------------------------------------------------
1) VERIFICACIÓN CONTRA EL FIRMWARE EXTRAÍDO (webui_full/):
   - scram.js: saltedPassword=PBKDF2-SHA256(pw, hex(salt), iter, 32);
     clientKey=HMAC(salted,"Client Key"); storedKey=SHA256(clientKey);
     clientSig=HMAC(storedKey, authMsg); proof=clientKey XOR clientSig.
     -> coincide EXACTO con webui_update.login_scram().
   - main.js: g_scarm_salt = CryptoJS.enc.Hex.parse(salt) (salt HEX,
     coincide con bytes.fromhex); authMsg = firstnonce + "," +
     servernonce + "," + servernonce (idéntico); mode=1 (RSA_LOGIN_MODE).
   - getTokenFromHeader: toma los PRIMEROS 32 chars del header rotado
     -> coincide con rotated_token() v[:32].
   - authentication_login.lua: al validar el proof el servidor VUELVE
     a rotar el token (web.setHeaderRequestVerificationToken "one"/"two"
     y el pool en "__RequestVerificationToken" con tokens separados por
     '#'). challenge_login.lua NO rota.

2) BUG REAL ENCONTRADO Y CORREGIDO EN webui_update.login_scram():
   El cliente leía la rotación del token SOLO tras challenge_login;
   tras authentication_login seguía con el token viejo -> la
   verificación state-login posterior habría devuelto 125003 y el
   login habría "fallado" AUNQUE la contraseña fuera correcta. Ahora
   se relee rotated_token() tras authentication_login (igual que el
   JS, que hace push del token del header en g_requestVerificationToken).

3) HERRAMIENTA NUEVA: test_scram.py (verificación OFFLINE end-to-end)
   Levanta un mock B612 que replica el lado servidor del firmware
   (SCRAM-SHA-256, serversignature, rotación con one/two/pool,
   state-login, sesión por cookie) con una contraseña CONOCIDA:

     python test_scram.py

   Resultado: TODOS LOS CHECKS OK
     [OK] contraseña correcta -> login True (State=0)
     [OK] token CSRF rotado tras authentication_login adoptado (32 chars)
     [OK] contraseña incorrecta -> False (108006)
     [OK] token CSRF viejo rechazado (125003)

   PRIMERA prueba que demuestra que el proof del cliente es correcto
   (antes solo había 108006 contra el router real, que es ambiguo).

4) api_b612.py actualizado a login SCRAM (--password obligatorio,
   --username/--host opcionales): la "puerta B" (sondeo de endpoints +
   comandos AT) ya no usa el login admin/admin falso.
